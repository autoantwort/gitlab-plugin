When enabled, every commit status update looks up the current pipeline for that commit (preferring a merge request pipeline) and explicitly targets it via pipeline_id, instead of letting GitLab decide based on the commit SHA, ref and status name alone.

Without this, GitLab treats (sha, ref, status name) as an identity: the first status update for a build either attaches to whatever pipeline already exists at that moment, or spins up a throwaway "external" pipeline if none does yet - and every later update for the same build keeps updating that same entry in place, even after GitLab's own pipeline for the commit is created. That can leave a build's final result invisible to anything that only looks at the merge request's head pipeline, such as "pipelines must succeed" merge checks.

This is off by default to preserve existing behavior. It can be overridden per gitlabCommitStatus / updateGitlabCommitStatus Pipeline step call.
